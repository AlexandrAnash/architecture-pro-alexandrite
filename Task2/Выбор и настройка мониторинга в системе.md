# Выбор и настройка мониторинга в системе

## Мотивация

**Что мы видим сейчас**
- Сайт подключен к Яндекс Метрике. Она видит только то, что делают посетители в браузере на нашем сайте
- Заказы партнеров через API идут s2s, без браузера — Метрика их не видит вообще
- Что происходит с заказом после кнопки "Сделать заказ" — расчет в MES, сообщения в RabbitMQ, CRM, базы, — Метрика тоже не видит. А заказы теряются и зависают скорее всего там

**Что даст мониторинг**
- Увидеть в цифрах, где проблема, прежде чем тратить месяцы разработки. Например, гипотеза, что страница операторов тормозит из-за расчетов цены, сейчас ничем не подтверждена
- Где проблема уже понятна из других источников (например, таймауты у партнеров при расчете до 30 минут), чинить можно параллельно — а мониторинг покажет, помогло ли
- Узнавать о проблеме раньше клиента: сработал алерт — команда уже разбирается, а не ждет жалобу
- Показать бизнесу "было / стало" после каждого улучшения
- Заранее видеть, когда растущая нагрузка (+100 заказов каждый месяц) упрется в возможности системы, и добавлять мощности до того, как все встанет

## Выбор подхода к мониторингу

- **Shop API, CRM API — RED** (Rate, Errors, Duration). Это сервисы, которые отвечают на запросы: важно, сколько запросов приходит, сколько из них с ошибкой и как долго отвечают
- **MES API — "Четыре золотых сигнала"**. т.к. кроме RED, важна насыщенность: расчеты цены идут до 30 минут и копятся, MES может захлебнуться
- **Shop DB, MES DB, RabbitMQ, 3d files storage — USE**. Это ресурсы: важно, насколько они заняты, сколько работы ждет и нет ли ошибок
- **Машины, на которых работают API, — USE**: процессор и память. У сервиса два взгляда: снаружи RED — как он отвечает, изнутри USE — не задыхается ли его машина
- **Фронтенды (Internet Shop, CRM, MES)** работают в браузере пользователя, их запросы уже учитываются на стороне API. Поведение пользователей в браузере частично видит Яндекс Метрика, но потом можно и фронты собирать у нас сделав им ручку. 

## Метрики

### API — RED, для MES API плюс насыщенность

- **Количество запросов** — одна метрика вместо отдельных RPS, HTTP 200 и HTTP 500 из списка
  - Зачем: Rate — сколько нагрузки приходит, Errors — сколько запросов закончились ошибкой.
  - Ярлыки:
    - `service` — shop / crm / mes
    - `status` — код ответа: 2xx, 3xx, 4xx, 5xx
    - `endpoint` — какой метод API вызвали
  - RPS, количество успешных ответов и количество ошибок считаются из этой одной метрики

- **Количество запросов по пользователям — только для MES API**
  - Зачем: видно, какой партнер сколько запросов шлет, кто засыпает повторами после таймаутов, кто создает основную нагрузку
  - Ярлык: `partner_id`
  - Для Shop API и CRM API считать по пользователю слишком жирно, пользователей много, но может быть полезно, например, если инцидент разбираем. 

- **Время ответа (latency)**
  - Зачем: Duration — как долго ждут пользователи. Для MES API показывает, тормозит ли страница операторов
  - Ярлыки: `service`, `endpoint` — у расчета цены и у списка заказов совсем разное нормальное время, в одной куче они смешаются
  - Медиана p95

### MES API — насыщенность (S из "Четырех золотых сигналов")

- **Очередь расчетов цены**
  - Зачем: сколько расчетов идет сейчас и сколько ждет. Очередь растет — MES не успевает, скоро будут таймауты у партнеров и тормоза у операторов
  - Ярлыки:
    - `state` — идет / ждет
    - `source` — магазин (B2C) / партнер (B2B): видно, кто создает нагрузку
  - После выноса расчета в воркеры этой метрикой станет длина очереди заданий в RabbitMQ — она же сигнал, что пора добавлять воркеров

- **Длительность расчета цены** (своя метрика)
  - Зачем: проверить, правда ли расчет идет 2–3 минуты, а сложный — до 30?
  - Ярлык: `complexity` — сложность модели группами (простая / средняя / сложная) по числу полигонов

### RabbitMQ — USE

- **Сообщения в dead-letter** — E
  - Зачем: каждое такое сообщение — заказ или смена статуса, которые не обработались. Любое значение больше нуля — повод разбираться

- **Сообщения in flight** — ближе к S
  - Зачем: получатели забрали сообщения, но еще не подтвердили обработку. Растет — получатели медленно обрабатывают или зависли
  - Ярлык: `queue`

- **Длина очереди** — S
  - Зачем: сколько сообщений ждет, пока их заберут. Растет — получатели не успевают. Для очереди заданий на расчет — сигнал добавлять воркеров
  - Ярлык: `queue`

- **Память и диск RabbitMQ** — U
  - Зачем: при нехватке памяти или диска RabbitMQ перестает принимать новые сообщения — встает передача заказов между всеми системами — инцидент!

### Базы данных (Shop DB, MES DB) — USE

- **Время выполнения запросов**
  - Зачем: понять, что тормозит у операторов — база или сам MES
  - Ярлыки: `db`, `query_type` (список заказов, смена статуса)
- **Количество подключений** — S
  - Зачем: упремся в лимит PostgreSQL — новые запросы получат отказ
  - Ярлыки: `db`, `app` (в Shop DB ходят и магазин, и CRM)
- **Память и CPU** — U
  - Ярлык: `db`
- **Размер базы**
  - Зачем: заказы копятся, заранее видно, когда кончится диск
  - Ярлык: `db`

### Машины API и хранилище файлов — USE

- **CPU и память для Shop API, CRM API, MES API** — U
  - Зачем: видно, не задыхается ли машина. У MES CPU — главный подозреваемый при расчетах
  - Ярлык: `service`
- **Размер S3** — U
  - Зачем: 3D-файлы копятся, заранее видно рост и стоимость хранения

### Бизнес-метрики заказов

- **Время заказа в статусе** (нефинальные статусы)
  - Зачем: заказ висит дольше нормы — завис. Ловим раньше жалобы
  - Ярлыки: `status`, `source` (магазин / партнер)
- **Количество заказов в каждом статусе**
  - Зачем: видно, где заказы копятся
  - Ярлыки: `status`, `source`
- Какие именно заказы зависли — смотрим в трейсинге или логах

## План действий

1. Поднять Prometheus (хранилище метрик), Grafana (дашборды), Alertmanager (алерты)
2. Подключать по влиянию на бизнес:
   - MES API и MES DB — метрики в коде MES, экспортер для PostgreSQL
   - Бизнес-метрики заказов
   - RabbitMQ — встроенный модуль для Prometheus
   - Shop API, CRM API, Shop DB — Spring Boot отдает метрики почти из коробки
   - CPU и память машин, размер S3
3. Дашборды: общий по заказам — для бизнеса, по каждой системе — для команды
4. Алерты: зависшие заказы, рост очереди расчетов, 504 у MES API, сообщения в dead-letter
