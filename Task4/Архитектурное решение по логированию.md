# Архитектурное решение по логированию

## Какие логи собираем

### Уровень INFO

Во всех записях: время, сервис, `trace_id`, `order_id`

- **Shop API**
  - заказ создан, 3D-файл загружен, заказ оформлен — `customer_id`, размер файла
- **MES API**
  - запрос от партнера принят — `partner_id`, id запроса
  - расчет начат / закончен — длительность, число полигонов
  - оператор взял заказ, изготовил, упаковал, отправил — `operator_id`
- **CRM API**
  - заказ получен (из магазина или от MES)
  - продавец подтвердил — `seller_id`
  - заказ закрыт — кем: транспортная компания или вручную
- **Все сервисы, работающие с RabbitMQ**
  - сообщение отправлено / получено — очередь, id сообщения. Есть "отправлено" без "получено" — сообщение потерялось

### Другие уровни

- **WARN** — странно, но работает:
  - повтор запроса от партнера с тем же id запроса — дубль пойман
  - расчет идет дольше 30 минут
  - повторная отправка сообщения в RabbitMQ
- **ERROR** — сломалось:
  - расчет упал (битый файл)
  - сообщение ушло в dead-letter
  - не удалось отправить сообщение, ответ 5xx
- **DEBUG** — в проде выключен. Включаем временно для одного сервиса на время разбора инцидента

## Мотивация

Сейчас ошибки разбирают со слов клиента. Он рассказывает, что пошло не так, а разработчики и поддержка долго ищут, что случилось внутри. Логи всех систем в одном месте, с `order_id` и `trace_id`, дают ответ поиском.

На что повлияет:
- **Время поиска причины инцидента** — техническая
- **Доля багов, закрытых с найденной причиной**, а не "не хватает логов" — техническая
- **Время ответа клиенту и очередь задач по жалобе клиента** — бизнес
- **Споры операторов, кто взял заказ** — решаются по логу — бизнес

## Очередность внедрения

0. **DevOps поднимает Collector и OpenSearch** — без них логам и трейсам некуда идти

Дальше параллельно, разными людьми:
- **Java (Shop API, CRM API)** — почти из коробки (агент OpenTelemetry, логирование Spring), первые логи за несколько дней
- **C# (MES API)** — самое ценное: там теряются контракты и висит гипотеза про тормоза операторов. Самая дорогая доработка, т.к. один разработчик
- **Во всех сервисах** — записи "отправлено / получено" для RabbitMQ и `traceparent` в заголовках. Заказы теряются на стыках, и без обеих сторон стыка картина неполная

## Предлагаемое решение

- **Структурированные логи** — сервисы пишут логи в JSON: каждое значение в своем поле (`order_id`, `trace_id`, уровень), а не одной строкой текста. По ним можно точно искать и считать
- **OpenTelemetry Collector** — тот же, что для трейсинга. Принимает логи, вычищает персональные данные, отправляет в OpenSearch
- **OpenSearch** — тот же, что для трейсов, логи в отдельных индексах
- **OpenSearch Dashboards** — веб-интерфейс для удобного поиск по логам, графики, алерты
- В Java-сервисах логи отправляет агент OpenTelemetry, в MES — библиотека OpenTelemetry для .NET

## Безопасность

- Не пишем в логи: фио, телефон, email, адрес доставки, карты, пароли, токены... Вместо них — `customer_id`, `partner_id`
- Collector дополнительно вычищает такие поля, если их записали по ошибке
- Доступ к логам: поддержка и разработчики — чтение, DevOps — администрирование. Продавцам, операторам и партнерам — нет
- Вход через корпоративную учетную запись и роль, OpenSearch Dashboards только во внутренней сети

## Хранение

- Отдельный индекс на сервис и день: `logs-shop-2026.10.12`, `logs-crm-...`, `logs-mes-...`. Удобно давать доступ по сервисам и удалять старое целым индексом
- 90 дней в OpenSearch для поиска — больше срока жизни заказа, с запасом на зависшие. Дальше архив в S3 на год-два
- Перенос в архив и удаление — автоматически, политиками ISM в OpenSearch
- Объем (оценка): заказов в кейсе не названо, допустим 2 000 в месяц. ~30 записей на заказ по всем системам плюс запросы партнеров и ошибки — около 0,5 млн записей в месяц. При ~1 КБ на запись: 0,5 ГБ в месяц, за 90 дней ~1,5 ГБ, с репликой ~3 ГБ. С запасом на рост и DEBUG при разборах — закладываем 10-20 ГБ

## Анализ логов

**Алерты**
- Всплеск ERROR в сервисе выше обычного уровня
- "Отправлено" без "получено" дольше 5 минут — сообщение потерялось
- Расчет дольше 40 минут
- Алерт приходит дежурному в мессенджер, с `order_id` и ссылкой на трейс
