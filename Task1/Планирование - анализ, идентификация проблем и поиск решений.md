# Планирование: анализ, идентификация проблем и поиск решений

## Анализ текущего состояния

### Процессы

- **Проблема:** e2e-сценарии прогоняет вручную один QA. Из автоматических тестов есть только юнит-тесты (запускаются перед деплоем в dev).
  - **Что настораживает:**
    - Каждые 2 недели добавляется новая функциональность, сценариев для ручной проверки становится больше, а автоматизации e2e нет. Нагрузка на тестировщика только растет, поэтому растут и задержки релизов (видим уже больше месяца).
    - Перегрузка: даже когда тестировщик на месте, он не успевает, и релизы задерживаются все сильнее.
    - Бас фактор: тестировщик заболел или ушел в отпуск — релизы встают полностью.
    - Для бизнеса: исправления критичных багов, в том числе проблем с заказами, доходят до продакшна с опозданием, и компания дольше теряет клиентов и контракты.

- **Проблема:** Деплой в prod выполняется вручную. У каждого приложения один инстанс
  - **Что настораживает:**
    - Деплой руками — большой риск ошибки, а с одним инстансом ошибка сразу ломает сервис для всех
    - Пока идет деплой, сервис недоступен: второго инстанса нет, все пользователи видят ошибку.
    - Если покупатель в этот момент загружал 3D-модель, соединение обрывается и негатив, как оно и бывает, 99% загрузилось и ошибка
    - Если MES в этот момент считал стоимость (от 2–3 до 30 минут), расчет обрывается. Этого никто!! не замечает, и заказ может зависнуть в статусе SUBMITTED (хотя может там есть ретрай)
    - Для бизнеса: это одна из возможных причин "потерянных" заказов, на которые жалуются клиенты и партнеры. О проблеме узнают только из жалоб

- **Проблема:** Деплой в release выполняется вручную, а потом ту же версию вручную ставят в prod
  - **Что настораживает:**
    - Ничего не гарантирует, что в prod поедет ровно та версия, которую проверял QA. Человеческий фактор максимальный
    - Если в prod поедет не та версия — тестирование считай делали зря, да еще могут быть проблемы с миграцией и т.п.
    - Для бизнеса: релиз ждали больше месяца, а в прод все равно может попасть непроверенный код

### Расчет стоимости в MES и API для партнеров

- **Проблема:** Расчет стоимости идет в MES от 2–3 до 30 минут, и его ждут сразу несколько сторон. Партнеры (B2B) ходят через API напрямую в MES — в тот же единственный инстанс, где работают операторы
  - **Кто ждет цену:**
    - Покупатель (B2C) в онлайн-магазине
    - Продавец в CRM — чтобы подтвердить заказ (MANUFACTURING_APPROVED). MES и CRM связаны через RabbitMQ
    - Партнер (API user) — ждет ответ от API
    - Оператор — косвенно: пока цена не посчитана и не подтверждена, заказа для работы у него нет
  - **Что настораживает:**
    - В задании не сказано, синхронный API или асинхронный. Если синхронный — запрос партнера висит до 30 минут, а таймауты обычно от 30 секунд до нескольких минут. Партнер получает ошибку, хотя MES продолжает считать и заказ в CRM потом все равно создается
    - Партнер думает, что заказ не создан, и отправляет повторно — получаем дубль. Два заказа на одно изделие: могут изготовить дважды или выставить счет дважды
    - Каждый повтор запускает новый расчет на том же инстансе — нагрузка растет, расчеты идут все дольше, таймаутов и повторов еще больше. Снежный ком
    - В это время операторы ждут загрузки первой страницы MES — похоже на их жалобу из кейса. Возможно, поэтому и не помогли фильтр с пагинацией: тормозит не список, а перегруженный MES
    - Если API асинхронный — в задании не описано, как партнер узнает цену и статус заказа. А партнеры как раз жалуются, что "не получили заказ"
    - Для бизнеса: один механизм может объяснять сразу три жалобы — партнеров, операторов и покупателей. Из-за проблем с заказами через API уже потеряны крупные контракты
    - Пока это гипотеза: метрик нет, проверить нечем

### Команда

- **Проблема:** MES куплен вместе с исходным кодом, значит дорабатывать его может только своя команда. А в команде один C#-разработчик (бэкенд MES), полноценного React-разработчика нет (фронт MES на React, один Vue-разработчик знает React частично). Тимлид — бывший C#-разработчик, но у него своя работа
  - **Что настораживает:**
    - Бас фактор: все фиксы MES ждут одного человека. Заболел, ушел в отпуск, уволился — работа по MES встает
    - Самые больные проблемы (долгий расчет, перегрузка, тормозящая страница операторов) как раз в MES. Скорость их исправления упирается в одного человека
    - Если C#-разработчик уйдет, исходный код у компании останется, но поддерживать его будет некому. Плюс "купили с исходниками" превращается в риск
    - Для бизнеса: компания теряет контракты из-за проблем в MES, а быстрее их не исправить, пока в MES один разработчик. Это обоснование для найма

### Путь заказа: магазин -> CRM

- **Проблема:** Магазин никому не сообщает о новых заказах (у Shop API нет стрелок ни в CRM, ни в RabbitMQ). CRM сам лезет напрямую в базу магазина (Shop DB) и, судя по схеме, периодически проверяет ее на новые заказы. Два приложения завязаны на одну базу
  - **Что настораживает:**
    - Команда магазина меняет структуру таблицы заказов (миграция) и не думает про CRM — CRM перестает видеть новые заказы, они зависают в SUBMITTED. Инцидент
    - Еще хуже, если CRM не падает, а молча читает не те данные
    - Поймать такое до прода некому: автотестов на связку магазин–CRM нет, ручное тестирование может не заметить если разработчик не подсветит

### Статусы заказа

- **Проблема:** В списке статусов нет статуса ошибки. Если расчет цены в MES упал (например, битый файл модели), заказ так и остается в SUBMITTED
  - **Что настораживает:**
    - Покупатель не узнает о проблеме и просто ждет, хотя мог бы, например, загрузить файл заново
    - По статусу SUBMITTED не отличить: расчет еще идет, упал с ошибкой, оборвался при деплое или CRM вообще не увидел заказ. Все выглядит одинаково
    - Для бизнеса: продавцы и поддержка не видят, какие заказы требуют вмешательства, — узнают опять из жалоб

## Проблемы

**Наблюдаемость**
- Нет мониторинга, логов и трейсинга — о проблемах узнаем только из жалоб

**Процессы: нет автоматизации тестирования и деплоя**
- Ручное e2e-тестирование одним QA — релизы задерживаются больше месяца, и задержки растут
- Ручной деплой при одном инстансе — во время деплоя сервис недоступен, расчеты и загрузки обрываются
- Ручной перенос версии из release в prod — нет гарантии, что в prod попадет проверенная версия

**MES и расчет стоимости**
- Расчет цены идет до 30 минут на единственном инстансе MES, куда напрямую ходят и партнеры через API, и операторы — таймауты, дубли, снежный ком нагрузки

**Интеграции и данные**
- CRM читает заказы напрямую из базы магазина — любая миграция в Shop DB может сломать передачу заказов
- Нет статуса ошибки — по SUBMITTED не отличить, идет расчет или заказ застрял

**Команда**
- MES дорабатывает один C#-разработчик, полноценного React-разработчика нет — бас фактор на самой проблемной системе

## Инициативы

**Наблюдаемость**

- **Внедрить мониторинг, логирование и трейсинг**
  - Делать до большой переделки MES — сначала измерь, потом лечи:
    - при переделке может что-то сломаться, а без наблюдаемости мы этого не увидим
    - нужно замерить "как было", чтобы потом показать бизнесу "как стало"
    - сначала проверить гипотезы (например, что операторы тормозят из-за расчетов). Иначе труд единственного C#-разработчика уйдет не на настоящую причину, а компания все это время продолжит терять контракты
  - Закрывает: "узнаем только из жалоб" — зависшие заказы и ошибки видно сразу, а не через месяц от клиента
  - Цена: инфраструктура для метрик, логов и трейсов плюс доработка всех трех приложений. Основная нагрузка ложится на DevOps, а он один.

**MES и расчет стоимости**

- **Перевести API для партнеров на асинхронную схему**
  - MES сразу отвечает "принято" с номером заказа и статусом, расчет идет в фоне — партнер не держит соединение, таймаутов нет
  - Результат партнер узнает сам по номеру заказа (запрос статуса)
  - Защита от дублей: партнер передает уникальный id запроса. Если MES такой id уже видел — возвращает существующий заказ, а не создает новый (идемпотентность)
  - Закрывает: таймауты, дубли, снежный ком повторов, пробел "как партнер узнает статус"
  - Цена: доработка в MES (а это один C#-разработчик), партнерам тоже придется переделать свою интеграцию — нужно предупредить их заранее и какое-то время поддерживать старую схему

- **Вынести расчет стоимости из MES в отдельный сервис (воркеры) с очередью в RabbitMQ**
  - MES API кладет задание на расчет в очередь RabbitMQ, воркеры забирают задания и считают. Результат возвращается в MES, MES ставит PRICE_CALCULATED
  - Пики не роняют систему: задания ждут в очереди, а не перегружают MES
  - Растет нагрузка — добавляем воркеров (горизонтальное масштабирование). Сигнал, что пора, — очередь заданий растет
  - Воркер упал или его перезапустили задача не теряется. 
  - Закрывает: перегрузку MES расчетами, тормоза у операторов (если гипотеза подтвердится), рост нагрузки, обрыв расчета при деплое
  - Цена: серьезная переделка MES — купленный продукт, разбираться в чужом коде, а C#-разработчик один. Плюс инфраструктура для воркеров, а DevOps тоже один

**Процессы**

- **Автоматизировать e2e-тесты силами текущего QA или дать разработчикам и нанять второго QA на ручное тестирование**
  - Текущий QA уже хочет заниматься автоматизацией и делал прототипы
  - Новый QA берет на себя ручное тестирование релизов, чтобы автоматизация не остановила выпуск версий
  - Начинать с самых важных сценариев — путь заказа от создания до производства (через магазин и через API)
  - Автотесты запускаются автоматически при каждом деплое в release
  - Закрывает: перегрузку QA, растущие задержки релизов, бас фактор (QA становится двое)
  - Цена: найм одного человека. Обоснование для бизнеса: исправления проблем с заказами ждут релиза больше месяца, а компания тем временем теряет контракты

- **Автоматизировать деплой в release и prod: одна сборка проходит все окружения**
  - Версию собирают один раз (артефакт с номером версии), и именно этот артефакт едет сначала в release, потом в prod.
  - Человек при деплое в prod только нажимает "поехали!", все шаги выполняет конвейер. Миграции базы — тоже шаг конвейера
  - Закрывает: риск, что в prod поедет не та версия, ошибки при ручном деплое, проблемы с миграциями
  - Цена: работа DevOps (он один) — настроить конвейер для трех приложений. Автодеплой в dev уже есть, его можно расширить, а не строить с нуля

**Интеграции и данные**

- **Магазин сам сообщает о новых заказах через RabbitMQ, CRM перестает читать базу магазина**
  - Когда покупатель оформил заказ (SUBMITTED), Shop API отправляет в RabbitMQ событие "новый заказ" со всеми нужными данными. CRM получает его из очереди
  - Прямой доступ CRM к Shop DB убираем — базой владеет только магазин
  - CRM зависит только от формата сообщения, а не от структуры таблиц — миграции в Shop DB больше не ломают CRM. Формат сообщения меняем по договоренности между командами
  - Опроса больше нет — заказ приходит в CRM сразу, лишней нагрузки на Shop DB нет
  - Риск: магазин сохранил заказ и упал до отправки события. Защита — Outbox: событие записывается в базу магазина вместе с заказом, а отдельный процесс отправляет его в RabbitMQ и после перезапуска дошлет неотправленное
  - Закрывает: зависимость CRM от структуры Shop DB, поломки при миграциях, нагрузку от опроса
  - Цена: доработка Shop API и CRM на Java — там два разработчика, это не самое узкое место команды

- **Сделать статусы заказа честными: промежуточные статусы, статусы ошибок и контроль зависших заказов**
  - Новые статусы: PRICE_CALCULATING (расчет идет) и PRICE_CALCULATION_FAILED (расчет упал, с причиной — например, "битый файл")
  - При ошибке покупатель или партнер получает уведомление и может загрузить файл заново
  - Тихие сбои (расчет оборвался при деплое, сообщение потерялось) статусом ошибки не поймать — его некому поставить. Ловим по времени: у каждого статуса свой нормальный срок, заказ висит дольше порога — алерт. Например, для расчета порог — час при максимуме в 30 минут
  - После алерта поддержка видит застрявший заказ и может перезапустить расчет кнопкой
  - Закрывает: "по SUBMITTED не отличить, что происходит", заказы, которые зависают без следа
  - Цена: доработка статусов в трех системах (магазин, CRM, MES). Алерты по времени опираются на мониторинг и трейсинг — значит, делать после наблюдаемости

**Команда**

- **Нанять второго C#-разработчика на MES**
  - Минимум три инициативы требуют доработки MES на C#: асинхронный API, вынос расчета в воркеры, новые статусы. Плюс подключение MES к мониторингу, логам и трейсингу
  - Один разработчик делает их последовательно, и на каждую уходят месяцы — а компания все это время теряет контракты
  - Двое разработчиков знают код MES — бас фактор снят
  - Нанимать как можно раньше: новому человеку нужно время, чтобы разобраться в чужом купленном коде
  - Фронт MES на React: доработок меньше (новые статусы, кнопка перезапуска расчета) — вместо найма прокачать Vue-разработчика, который уже частично знает React
  - Закрывает: бас фактор на MES, узкое место для главных инициатив
  - Цена: найм одного человека

## Приоритизация
**Сразу, параллельно**
- Observability — сначала измерять будем потом уже лечить на основе данных и показать бизнесу "было / стало" легче.
- Найм второго C#-разработчика и второго QA — поиск и вход в чужой код MES займут месяцы, поэтому начинать в первый же день. Разработчиков найм не занимает

**Параллельные дорожки, не зависят от C#**
- QA: автотесты — после прихода второго QA, иначе ручное тестирование встанет и релизы остановятся
- Java: магазин сообщает о новых заказах через RabbitMQ
- DevOps: автодеплой одной сборкой — после основной части наблюдаемости, DevOps один и сразу обе не потянет

**Дорожка C#, по порядку**
1. Асинхронный API — напрямую бьет по главной потере денег: партнеры и крупные контракты. Останавливает таймауты, дубли и снежный ком повторов. Это доработка одной части MES, а не переделка всего
2. Честные статусы — продолжение асинхронного API: партнеру нужно честно отвечать "расчет идет" или "расчет упал". Алерты на зависшие заказы — после наблюдаемости
3. Вынос расчета в воркеры — последним: большая переделка, сначала нужно метриками подтвердить гипотезу, что операторы тормозят из-за расчетов, и дождаться второго C#-разработчика. К этому времени асинхронный API уже остановит снежный ком, и давление на MES снизится

## Целевая архитектура через полгода

**Что изменится на схеме C4**
- Появится стрелка Shop API -> RabbitMQ: магазин сам сообщает о новых заказах
- Исчезнет стрелка CRM API -> Shop DB: базой магазина владеет только магазин
- Появятся хранилища метрик, логов и трейсов с интерфейсами для просмотра (дашборды, поиск по логам, просмотр трейсов). Данные в них шлют все приложения, RabbitMQ и базы данных
- Появятся алерты от мониторинга к поддержке — о заказах, зависших в статусе дольше порога
- MES API для партнеров работает асинхронно: сразу отвечает "принято", партнер узнает статус по номеру заказа
- У заказа появятся статусы PRICE_CALCULATING и PRICE_CALCULATION_FAILED


## Три главные инициативы на полгода

1. **Наблюдаемость (мониторинг, логи, трейсинг)** — Зависшие заказы и ошибки видно сразу, а не из жалоб, гипотезы проверяются метриками, а бизнесу можно показать "было / стало"
2. **Найм второго C#-разработчика** — страховка от бас фактора на самой важной системе: если единственный C# разработчик уйдет, некому будет ни доделать асинхронный API, ни поддерживать MES. Заодно за полгода новый человек разберется в коде MES, и следующий этап (воркеры, статусы) начнут сразу двое
3. **Асинхронный API для партнеров** — без него через полгода партнеры все так же получают таймауты, шлют повторы (плодят дубли), а компания продолжает терять контракты. Это главная потеря денег, ради которой все и затевается
